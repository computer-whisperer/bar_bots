# Target design: the pianist. Opus plays the game, Jev plays the keyboard

Written 2026-09-21 at the user's direction. The user's framing: an RTS is "piano chess"; Opus plays the chess and
needs Jev (TypeSafe's System One model, `docs/harness/jev.md`) to play the piano. The heuristic pile names discrete
macro objectives piecemeal, and every one of them is blind to the others' claims on the same metal, build power and
soldiers; a player has to weigh raids, scouts, army moves, defences and the build order at once. Rulings:

- Opus is the player. It writes prose instructions; Jev reads them every second and picks each unit's next action from
  a menu the code offers. Opus iterates game to game on its instructions instead of on heuristic development.
- The economy planner (`docs/design/2026-09-21-rolling-planner.md`) is not in the loop: Opus dictates the build order
  to Jev. If that fails the fallback is a hybrid with the planner as the economy actuator under Jev's allocation.
- The heuristic brain stays as it is, untouched, as the baseline opponent in batches and as the control. It is not
  the pianist's fallback: when the pianist beats it, it is deleted. Shadow mode over the heuristics' own decision points
  was considered and rejected: it would measure Jev on the framing this design says is wrong.
- Evaluation cost is no objection: the arena runs the shim in lockstep (`WITHIN_REASON_LOCKSTEP`), so a call held on
  the tick pauses the game rather than going stale, and Jev's limit is 1,200 requests a minute (20 a second across all
  parallel games), which at one call per game-second is about today's batch throughput. Opus games are already real
  time. Live GUI games see the call's latency, about 320 ms, which is fine at 1 Hz.

## What is true today
- `crates/bot/src/brain/`: the heuristic brain, `Brain::decide` per tick (10 Hz): the control lane (`micro.rs`: flee,
  fan, focus, kite, on the threat grid) every tick, `think` at 2 Hz: tracking (`track_*`, `survey_spots`, territory,
  wrecks, losses), then the decision heuristics (`protect_commander`, `run_economy` with the planner and the rule
  ladder, `run_army` with contact, raid, scout, waves, squads), then the briefing and the wake conditions for the
  LLM session.
- `crates/bot/src/strategist/`: one `claude -p` session per team beside the brain, an MCP server on 127.0.0.1, modes
  `Strategist` (standing directives) and `Commander` (turns when woken, the game held still meanwhile; tools
  `overview`, `situation`, `map`, `set_directives`, `squad`, `set_production`, `request_turret`, `expansion`,
  `orders`, `wait`, `note`). The prompt is `commander.md` plus `docs/briefs/commander.md`.
- Jev: first contact 2026-09-19 (`experiments/jev/`, `docs/harness/jev.md`): `POST /v1/systemone`, state plus typed
  questions (Choice up to 255 options, Noul, Score up to 10 levels), all answered in parallel over one state,
  probabilities and confidence back, 318-350 ms from this machine, 64k context (32k for the state plus the longest
  question), $0.042 per million input tokens, output free. Documented weaknesses: arithmetic, counting, comparing
  quantities, dates, multi-hop reasoning, distraction by unrelated state. Answers are not bit-stable. It cannot
  choose an option it was not offered. The key lives in `~/.config/within-reason/jev.env` or `TYPESAFE_API_KEY`.
- No HTTP client crate in the workspace (`tiny_http` serves the MCP server); the record format already reserves
  decision records with `source: "jev"` (`docs/harness/record-format.md`).

## The change

### Layers
```
 Opus (claude -p, mode Player)        writes  ─►  the packet: standing instructions in prose, rewritten each turn
        ▲ woken by the wake rules and by Jev's own "this needs the player" answer
 Jev (the pianist, 1 Hz)              reads   ─►  state = packet + rules + the picture; answers one menu per actor
        ▲ the hands: picture writer, menus, actuators, commitment, the record
 engine (commands per tick)                        the control lane (flee, fan, focus, kite) unchanged beneath
```

### The pianist (`crates/bot/src/pianist/`, a mode of the bot: `bot --pianist`, `--pianist --player` with Opus)
Every `PIANIST_FRAMES` (30, one game second; `WITHIN_REASON_JEV_INTERVAL` overrides) the pianist:
1. **Writes the picture** (`picture.rs`): one JSON state. In this order: `instructions` (the packet, or a default
   opening text until Opus writes one), `clock`, `rules` (short standing facts: what wins, what the opponent does,
   what the menu words mean), `economy` (each quantity as a word and a number: "metal 120 of 1000 stored, nearly
   empty; income 12 a second, spending 18: stalling"), `ours` (extractors by spot number, labs, constructors, turrets,
   the army as groups), `enemy` (parties in sight as named places and compositions, remembered buildings, the
   commander if seen, what was lost where lately), `map` (spots by number: ours, theirs, free, exposed, raided;
   named places), `actors` (one entry per actor: what it is, where, what it is doing and since when, its health),
   `recent` (events of the last 30 s). Written by actor, not as one dump, and qualitative first: numbers follow the
   words. Under about 4k tokens; the writer logs its size.
2. **Offers the menus** (`menu.rs`): one Choice per actor that is *free* (idle, its task done or refused, or its
   commitment expired), always with a "continue" or "nothing" option:
   - the commander and each constructor: continue; an extractor at spot N (each free reachable spot among the nearest
     eight); a generator, lab, turret, radar, converter, storage or construction turret near here; assist the nearest
     lab; reclaim the nearest wrecks; repair the nearest damaged unit; walk to a named place; retreat home;
   - each lab: the next unit from its buildable list, or nothing (save the metal);
   - each soldier group: hold; move to a named place; fight to a named place; engage an enemy party in sight; retreat
     home; join another group; and a `split` question (send the nearest N of a type to a place as a new group) when
     the group has more than one type;
   - global Nouls: the base is in danger; a large attack is coming; this needs the player's attention now.
   Destinations and targets are separate Choices consumed only when the action needs them (speculative fan-out):
   `where` over the named places and `whom` over the parties in sight. Named places: metal spots by number, home, the
   enemy start, the grid cells. Two questions per group, one to three per builder, one per lab, three global: 30 to
   100 a second at full size.
3. **Asks** (`crates/jev`): one request. In lockstep the tick waits for the answer (the game is held, as for the
   commander's turns); against a live engine the request runs on a thread and the answer lands next tick, the
   previous decisions standing meanwhile. A 429 waits for `retry-after`; any other failure leaves every actor on its
   current task and is logged; the pianist plays nothing new until the next answer.
4. **Plays** (`hands.rs`, `groups.rs`): each answer becomes orders through the existing actuators: build sites and
   extractor placement (`economy.rs` `build_site_for`, `extractor_site`, `beside_builder`), walking (`routes.rs`),
   the march (`march.rs`), the squad post response for `engage` (as many of the nearest as the odds take, `squads.rs`),
   the factory queue. Groups: new soldiers join the `pool` group at their lab; a group is a set of soldiers with a
   task; `split` makes a new one, `join` merges. Commitment: an actor's task holds until done, refused or its
   time is up (a move until arrival or 20 s; a build until started or refused; a lab unit until queued), and a
   *free* actor switches from "continue" only when the winning option beats it by `SWITCH_MARGIN` (0.15) in
   probability, so wobbling answers do not flip units every second.
5. **Records**: a `d` record per answered question (`source: "jev"`, `kind`: the actor kind, `inputs`: the actor's
   entry and its options, `outputs`: the choice, its probability, the confidence, `latency_ms`), and with
   `WITHIN_REASON_JEV_LOG=1` (the arena sets it) the whole request and response per call to `jev-<ai_id>.jsonl` for
   study. The API key is never logged.

What stays beneath the pianist: the control lane, unchanged; the tracking (`track_*`, `survey_spots`, territory,
wrecks, losses); the briefing and wake rules for Opus; the per-minute status line. What does not run under it: every
decision heuristic in `economy.rs`, `army.rs`, `contact.rs`, `raid.rs`, `scout.rs`, `planner.rs`, `protect_commander`,
`squads.rs`' order taking. The pianist reads no directive.

### The player (strategist mode `Player`; refined 2026-09-21 evening, the user: "Let's work on the player next")
`bot --pianist --player`: a `claude -p` session (Opus) beside the pianist, run as the commander is (lockstep: the game
held still during a turn; forty turns a session, then a fresh one handed the notes and the instructions in force).
- **Its lever is prose.** `instruct { text }` replaces the standing instructions whole; the pianist's next picture
  carries them (the game is held during the turn, so they land the moment it ends). No directive, squad, production
  or turret tool is offered: what the player wants of a unit it says in words and Jev picks the menu option. The
  packet is capped at 8,000 characters (Jev reads it every second beside a picture of about 4k tokens).
- **What it sees.** The turn report opens as the commander's does (score, traded, eco, ground, wrecks, to win, to raid,
  curves, fights, enemies in sight, extractors under threat: the lines that describe the game rather than the
  heuristics), then the hands: every group with its composition, place and task, every builder with its task, every
  lab with its queue, Jev's global judgements when they are high (base in danger, attack coming), and what the hands
  did since the last turn (the `did` lines, capped at forty). `situation` returns the picture Jev is shown, without
  the instructions and rules: the player reads exactly what its hands read. `overview` and `map` as today.
- **Woken** as the commander is (its `wait` settings: a quiet-time maximum, enemies near an extractor, an extractor
  lost, soldiers of a type reaching a count; a group starting an engagement in place of a squad's; the four-minute
  stagnation wake it cannot switch off), and by the hands: when Jev's `needs_player` Noul is at or above 0.8 for
  three calls running, at most once a minute (H-HANDS-PLAYER-WAKE).
- **What the pianist publishes for it** (`Shared.hands`): the last picture, the hands' `did` lines since the last
  turn, the group names engaging, and the global probabilities. The brain also keeps the growth and history tracking
  and publishes the field in pianist mode (they ran only inside the army heuristics before), so the score, curves and
  wake conditions work under the pianist.
- **Not covered:** `--think-penalty` delays directives, field orders and wake settings; the instructions land at once.
  A live-game latency for the player is a later step if the penalty matters here.
- **Read afterwards** with `run/commander_turns.py` (the transcript) and the viewer (the turns as `llm:player`
  decisions beside the pianist's calls). Each game's lessons go into `docs/briefs/player.md`, the knowledge the role
  prompt is followed by, as the commander's brief does.

### Arena
`--pianist` (the bot in pianist mode, heuristic-free, the default packet); `--pianist --player` (Opus on top; the
commander's `--commander-model`, `--effort`, `--claude-config-dir`, `--think-penalty` apply). Both set
`WITHIN_REASON_JEV_LOG=1`. Placement (`--place`) keeps using the build-order search: it is pre-game, not in the loop.
Batches with the pianist run `--parallel 6` at 1 Hz (the request limit).

### Docs
The pianist's mechanical rules (commitment, the switch margin, group formation, menu limits) are heuristics with IDs
`H-HANDS-*` in `docs/heuristics.md`; the question set and the picture's shape are recorded in `docs/harness/jev.md`
with every measured change; each game of the series gets a ledger row; the player's brief is `docs/briefs/player.md`.

### Audit (added 2026-09-21 evening, the user: "give me visibility into what jev is doing throughout the match")
The pianist's log is the audit's source (`docs/harness/record-format.md`, "The pianist's log"): one line per call with
the picture, the questions, the answers, what was played and why a course was kept, and the groups, places and parties
by name. The viewer (`viewer/`) reads it beside the record: every actor of the call at the playhead with its last
decision, the call itself as answer bars with the options as worded and the picture by section, per-minute call
statistics, pianist lanes on the timeline, the names and the groups' movements on the map, and an actor filter on the
decision list. The record's own `d` records (source `jev`) stay the compact form for lanes and the list. Held to the
same tests as the rest of the viewer (`viewer/test/`), with the pianist's panels added to the browser test.

## Steps
1. `crates/jev`: a blocking HTTPS client (a small TLS-capable crate; nothing async), request and answer types,
   the key from the environment or the key file, timeout, 429 with `retry-after`, the versioned model id logged.
   A `jev` binary that sends `experiments/jev/*.json` reproduces the probe.
2. The pianist without Opus: picture, menus, hands, groups, the record. One smoke game against BARb medium at the
   usual settings, read call by call: latency, state size, what it chose, how often a free actor's answer flipped.
   Then 12 games for the ledger against the heuristic bot's numbers.
3. The player: `player.md`, `instruct`, the pianist's log in the turn report, the wake Noul. Games one at a time on
   claude2 as the commander series, each read and integrated into `docs/briefs/player.md`.
4. What the games say decides the next: the picture's shape (whole-game against per-actor), the menu, the interval,
   whether the planner comes back as the economy's hands.

## Judged by
- Step 1: the three probe scenarios answer as on 2026-09-19 (escort 0.72; attack 0.03; return_and_defend 0.93).
- Step 2: the smoke game plays a whole game from a default packet without a heuristic; the flip rate of free actors'
  answers second to second; economy at 5 and 10 minutes against the heuristic batch (planner-2: 9 / 9.5 extractors,
  income 18 / 18) with the same setup (medium, mirror, `--place`, `--corner nw`).
- Step 3: the commander series' measure: games won, minutes survived, extractors by minute 10, and what Opus asked
  for that the menu could not express.

## Footwork per group, and the milling instrument (2026-09-21 night, the user's ruling)

The user: keep the gap between the hands and the game small and predictable; Opus and Jev must be able to take units
and "just order it to do something without our micro engine getting in the way"; some lane rules were never tested
apart, and units "mill about rather than decisively moving towards or away from a threat" because the lane's model
(a point moving at full speed in any direction at once) does not match a unit that turns and accelerates slowly.

- **H-HANDS-LANE.** The player's `lane` tool sets, per group (`group_A`) or for `all`, which of the six footwork rules
  apply: `flee`, `fan`, `focus`, `kite` (the control lane, `micro.rs`), `march` (H-ARMY-MARCH on `fight_to`) and
  `follow` (an engaging group re-sent after its party). `"raw"` is none of them: the group's Fight and Move orders go
  to the engine as the hands gave them. `"on"` is all of them, the default. A list keeps those named. The setting is by
  group name and stands until changed; the group's picture entry shows it when it is not the default, so the report
  carries it. Jev never sets it: it is a standing state the player judges.
- **The milling instrument.** While the lane holds a claim on a unit it sums the path the unit walked, the net
  displacement from where the claim began, and the reversals (a step more than ninety degrees from the last). When the
  claim ends the three go into the journal and the record's next sample as `lane: [claims ended, path, net,
  reversals]`; `run/micro_ledger.py` prints path over net and reversals per claim. Hysteresis in the flee is the first
  candidate fix, to be judged by these numbers in an A/B, not before.
- **The game-4 gaps.** A hold that follows an advance keeps the advance's commitment (`Hold { committed: true }`), so
  the ball that fought into the base keeps fighting there; `engage` is committed to the commander when the group is
  the raid's size for it (`COMMANDER_PARTY_METAL`), as the heuristic answers are.

## Realtime (2026-09-22, the user's ruling: "the main requirement for realtime is to disable pausing")

Built for a game against people, and rehearsed headless first:

- `WITHIN_REASON_REALTIME` on the bot (the arena's `--realtime`: speed 1, no engine lockstep). Nothing waits: the
  brain requests a turn without holding (`Shared::request_turn`; a request during a turn is dropped, the next report
  carries the state), the player is told in its first prompt that the game runs on and its orders land when the turn
  ends, and a turn with no answer after 120 s is abandoned and the session replaced (45 s in lockstep).
- The pianist asks Jev on a worker thread. One request in flight at a time, numbered; the answer is played on the
  tick it arrives against the picture and menus it was built from (a call's latency old, 200 ms); an answer that has
  not come after 3 s is dropped and the actors keep their tasks; an answer to a dropped request is discarded. In
  lockstep the call is made in place as before, since at speed 50 a wall-clock wait is ten game seconds.
- Judged by: the record's `late` field (ticks the shim sent late for want of an answer), the pianist's status line
  (calls, failed, dropped, median latency), the transcript's turn wall seconds, and the game itself against hard.

## The player's learnings, chat, and the versions (2026-09-22)

**What the player carries between games today.** One thing: `docs/briefs/player.md`, in its system prompt, written by
the harness's author after each game from the player's closing sentences and the record (13 game entries by game
13, 15 KB, about a fifth of the prompt). Its own notes live for one game (they cross session restarts, not games).
The knowledge base and the heuristics ledger are the harness's memory, not the player's. So the learnings are
single-author, one opponent (BARb) on one map (Quicksilver, north-west start), appended in order, never retired, and
never measured for whether a lesson changed play.

**The method proposed (the user: "a clean method for continuing integration"):**
- The brief split into layers the harness assembles per game: the game (units, economy, fights), the opponent
  (BARb by tier; people), the map (Quicksilver; each new map its own file), the scenario (1v1; 2v2 and tier 2). A
  lesson is one line with its source game and a status: held (cites games it held in), contradicted (by which game),
  retired. The assembled brief for a game is the layers that apply, held lessons first.
- The player writes its own debrief. After a match, `run/debrief.py <match>` runs one `claude -p` over the transcript
  and result (no game held, a few thousand tokens) and asks for at most five lines for the next player on this map
  and opponent, and what it wished it could order. The lines land in `docs/briefs/inbox/<match>.md`. Integration is a
  review pass, by the author or a session asked for it: promote to a layer, merge with what is there, mark
  contradictions. The ledger row cites the lessons the game used, from the player's notes.
- Growth is bounded by retirement: a lesson not cited in ten games of its layer is retired to the layer's archive.

**Chat.** The engine's message event now reaches the player: chat lines from people in the game come in the report
("chat since your last turn"), a chat line wakes it (the `wait` flag `chat`, on by default), and the `say` tool
speaks to everyone in the game. The prompt tells it that an experienced player watching is the feedback this
project learns from: answer, say what it is doing, ask what they would do.
